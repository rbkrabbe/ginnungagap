## Context

`AdminService.RemoveNode` on the target retires the node locally
(`admin_service.rs:326`) and cancels the shutdown token; `main.rs:428` reacts
by cancelling the rest and exiting ~500 ms later. `GossipTask::run`
(`gossip.rs:104`) selects on that cancellation before its next tick, so
`persist_directory` never runs between the retire and the exit. The tombstone
the node just wrote for itself is only in memory when the process dies.

The boot guard at `main.rs:276` — which exists so a retired node refuses to
start — then reads a persisted directory with no self-tombstone and lets the
node come up. It is refused only on the *next* restart, after gossip has
re-taught it its own tombstone, so the window is a full zombie boot: the node
rejoins, serves, and is dialled by peers that have already retired it.

tk-c47e's reviewer saw this shape and parked it on tk-ad1d for the
tombstoned-on-its-behalf path, where the node is dead and cannot flush
anything. It also hits graceful self-retirement, where the node is alive and
could — and that is the path the guard was written for. `main.rs:276` has no
test.

## Blast radius

`crates/ggap-server/src/admin_service.rs` (the retire path),

### Q1 [answered 2026-10-10T15:30:07+00:00] How does a self-retiring node get its tombstone onto disk before it exits?
- a) Write through in retire() — RemoveNode persists the directory synchronously before answering, so the tombstone is durable no matter how the shutdown races; costs a blocking write on an admin RPC
- b) Flush in GossipTask's shutdown arm — the task persists once more on cancellation, keeping all directory writes in the one place that owns them; still lost if the process dies without running the arm
- c) Both — write through on retire and flush on shutdown, since they cover different failures (a crash mid-retire vs. any other in-memory drift)
> Write through in retire(), and move directory persistence into ShardRegistry. RemoveNode returns ok:true meaning 'I am retired' and the process exits immediately after, so the tombstone must be durable before that response is sent; a flush racing the 500ms shutdown sleep is not a guarantee for an operation that cannot be taken back. The registry owns the directory, so it owns writing it: GossipTask stops holding a DirectoryStore and calls registry.persist() instead, which moves the dirty-check state with it, and retire() persists inline. Keep the shutdown-arm flush as well — three lines, and it catches in-memory drift at any shutdown rather than only this one.

## Outcome (2026-10-10)

Directory persistence moved into `ShardRegistry`, which owns the directory and
now owns writing it. `GossipTask` no longer holds a `DirectoryStore`; it calls
`registry.persist_directory()` after each round and once more in its
cancellation arm, so what a node learned since its last round does not go with
the process. The unchanged-since-last-write memo moved with the store, under a
mutex held across the write so two callers cannot both decide nothing changed.

`retire` writes through and returns `Result`. The two call sites want different
things from a failure, which is the part worth knowing:

- **On behalf of an unreachable node** (`admin_service.rs:255`): warn and carry
  on. This node keeps running, so its next gossip round persists the tombstone
  anyway.
- **Retiring itself** (`admin_service.rs:350`): log an error and *still* shut
  down. The broadcast to peers happens before this point and cannot be taken
  back, so refusing to exit would leave a node running that the cluster has
  already forgotten — the exact state the path exists to avoid. The order is
  deliberate and was already reasoned out in the code: a tombstone nobody else
  has heard must not be recorded, so the handover comes first and the local
  write is necessarily past the point of no return.

### Fixed after review

**A lost-update window in `try_persist_directory`.** The snapshot was taken
*outside* the mutex meant to protect it, so a caller could save a directory it
read before another caller's write: the later writer records its state, the
earlier one then overwrites the file with its stale snapshot, and the memo now
agrees with the file so nothing ever rewrites it. A `retire` losing its
tombstone that way would have returned `Ok`, reported durability, and exited
the process — precisely the failure this task exists to close. The snapshot is
now taken under the lock. Lock order is `persisted` then `directory`, and
nothing takes them the other way, so there is no inversion.

Review added a reason the fix is stronger than "the snapshot is inside the
lock": a snapshot taken before an insert can still reach disk, but the
inserting caller then takes the lock, re-snapshots, differs from the memo and
rewrites. The memo can no longer end up agreeing with a file that lacks a
tombstone, which was the unrecoverable half.

Deliberately untested. The window needs OS preemption between two statements
with no await point between them; review ran 200 contended iterations without
reproducing it, so a test would pass whether the bug were present or not. The
fix is structural and the reasoning is in the comment, which is the honest
place for it — a probabilistic test here would only look like coverage.

Also fixed: `ggap-storage/src/directory.rs`'s module doc still named the gossip
task as the writer, sitting directly above `save()` — the one file the next
person editing it would read, and missed by a sweep that covered
`docs/ggap-storage.md` instead.

`a_tombstone_survives_a_restart_and_the_gossip_that_follows_it` no longer calls
the gossip-persist helper: `retire`'s own write makes it redundant, and the
helper's assertion ("the gossip task never persisted…") was being satisfied by
a write the gossip task did not make. It now asserts the write-through
directly, which is what that test should have been pinning all along.

The directory-persistence tests needed their registries to carry the store,
since the gossip task no longer does. That is the whole behavioural surface of
the move: nine construction sites in `directory_persistence.rs`, one in
`three_node_cluster.rs`, one in `main.rs`.
