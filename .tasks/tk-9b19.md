## Context

A node's id comes from `--node-id` on every start and is written down nowhere.
`counter_key()` is `node_key("boot_counter")` — a bare label, not keyed by id —
so a node restarted with a different `--node-id` on the same data dir simply
keeps counting from where the last id left off. Nothing anywhere notices that
the process now claims to be someone else.

That silence is what makes the state dangerous rather than merely wrong. Raft
RPCs carry no target node id: `AppendEntriesRequest` and `VoteRequest` hold a
vote and log ids, and the envelope is `RaftMessage { shard_id, data }`. A node
answers whatever reaches its port for a shard it hosts, whichever id the sender
thought it was addressing. So a process restarted as 99 at the address peers
know as 42 keeps serving as 42 — replicating, and voting — while publishing a
second directory entry under 99. Both entries point at one process, and nothing
retracts the first (tk-c47e).

The data dir already holds the evidence: the persisted directory's self-entry is
written under the old id. There is just no check. A durable id record beside the
counter, in the same `node` keyspace, makes the rename detectable at the only
moment it can still be refused cheaply — before the node starts serving.

## Relationship to tk-8d80

Complementary, not a substitute. This closes the rename-with-data-dir-intact
path. A **wipe** plus a new id at the same address still produces two directory
entries for one process, because a wipe clears this record along with everything
else. tk-8d80's reverse address check is what catches that, so neither task
supersedes the other and neither blocks the other.

## Acceptance

- [ ] Starting with a `--node-id` that differs from the persisted one fails the
      boot, naming both ids.
- [ ] A first boot on an empty data dir records the id and starts normally.
- [ ] A wipe still permits a fresh id, since the record goes with it.
- [ ] `docs/ggap-node.md` documents the new refusal beside
      `cannot establish this node's incarnation`, and CLAUDE.md's `node`
      keyspace list names the record.
- [ ] Full checklist green: fmt, clippy -D warnings, build, test.

### Q1 [open] Is there any way to start with a changed node id, or is the refusal absolute?
- a) Absolute — the only route to a new id is a wiped data dir, which is already what CLAUDE.md tells an operator to do when an address change accompanies a wipe. No flag to misuse.
- b) An explicit --force-node-id override that rewrites the record. Allows deliberate renumbering without losing the Raft log, but the flag's only purpose is bypassing a safety check.

### Q2 [open] The id record is present but unreadable. Fail the boot, or treat it as absent?
- a) Fail, mirroring BootCounter::advance, which would rather refuse than proceed on a rank it cannot establish. Consistent, but makes one corrupt record in the node keyspace a hard outage.
- b) Treat as absent and rewrite it. The node starts and the id is re-recorded, but a corrupted record silently permits exactly the rename this task exists to refuse.
