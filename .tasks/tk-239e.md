## Context

tk-98e9 Q1 settled that node facts get their own keyspace rather than a fake
shard prefix. Two records qualify, and both move here.

**The directory**, shipped by tk-c593 under `keys::NODE_SCOPED` — that was
option (a), built before the question was answered.

**The shard map**, which the answer left open and which the evidence settles.
Its records are node-scoped state keyed by shard id, not shard-scoped data:

- The `be_u64(shard_id)` constraint exists so `[be(N), be(N+1))` isolates one
  shard's bytes. Shard map records sit under the sentinel, so a scan of shard
  N's key space never sees them and they get none of that property.
- `shard_map_key` formats the id as *decimal* in the label, so `"shard:10"`
  sorts before `"shard:2"`. Every genuinely shard-scoped key here is big-endian
  so lexicographic order equals numeric order. Harmless — `load` rebuilds a
  `BTreeMap<ShardId, _>` in memory — but it shows these were never treated as
  ordered per-shard data.
- The content is a node fact: `all_shards()` is what `main.rs` uses to decide
  which Raft groups *this node* starts. `remove_shard` has no callers, so there
  is no per-shard lifecycle on these records either.

Moving both retires `keys::NODE_SCOPED` completely: `meta` becomes purely
shard-scoped, and the constraint gets one rule and one named exception rather
than an exception hiding inside an exception.

## Changes

- New `node` keyspace on `FjallStore`; keys are bare labels, no shard prefix.
  It stays in the same fjall `Database` — cross-keyspace batches must keep
  spanning it, because a split writes its shard map records in the same atomic
  batch as data movement and `last_applied`.
- `DirectoryStore` and `ShardMap` both move to it. `shard_map_key` loses the
  sentinel and should take the chance to key by `be_u64(shard_id)` within the
  keyspace, so scan order finally matches numeric order.
- Delete `keys::NODE_SCOPED` and `SHARD_LABEL_PREFIX` once nothing uses them.
- CLAUDE.md: the constraint narrows to "all keys in *shard-scoped* keyspaces are
  prefixed with `be_u64(shard_id)`", naming the `node` keyspace as the exception.
- `docs/ggap-storage.md` (node-scoped-meta-keys and `DirectoryStore` sections)
  and `docs/ggap-consensus.md` ("one `meta` record") both need updating.
- Tests to revisit: `directory.rs::the_shard_map_ignores_the_directory_record`
  loses its subject, and the corrupt-record test in
  `ggap-consensus/tests/directory_persistence.rs` reaches for the key via
  `meta_key(NODE_SCOPED, "directory")`.

No migration: tk-ef8d Q2 wipes the data dir for format-breaking changes. But a
node meeting an old data dir must still *start* — the old records are simply not
found, which is an empty directory (fine) and an empty shard map (which
`initialize_default` refills as a fresh shard 0).

Blocked on tk-d9a8 deliberately. The split batch this touches is covered by
`split_crash_bugs`, which never runs: it is gated behind `required-features =
["test-utils"]` and neither the checklist nor CI enables it. Do not move shard
map writes while that safety net is switched off.
