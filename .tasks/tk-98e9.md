## Context

Epic tk-ef8d Q1 settled the clock that orders a node's descriptors: a boot
counter persisted in the data dir, incremented each start. tk-8978 built
everything that consumes it — `NodeDescriptor.incarnation`, the highest-wins
merge rule, and self-publication each gossip tick — but nothing writes the
counter. `main.rs` passes the constant `SELF_INCARNATION = 1`.

That is correct for a first boot and wrong for every one after it: a node that
restarts at a new address republishes at incarnation 1, which does not outrank
the incarnation-1 copy its peers already hold. The move still converges — the
moved node is the only source re-asserting the new address, the rank-0
membership feed cannot reintroduce the old one above rank 1, and no peer
regenerates it once flipped, so "every peer holds the new address" is the only
absorbing state. But it converges by arrival order rather than by rank, with an
oscillating transient rather than a guarantee.

The transient is longer than it looks. Ties go to the incoming entry, so a
peer's stale copy of the moved node's descriptor overwrites that node's *own*
self-entry in `merge_gossip_state`; `exchange_with` re-snapshots per peer, so
the node can re-emit the stale address about itself to the next peer in the
same round, until `refresh_local` restores it. Sole authorship — the property
the descriptor model exists to provide — is briefly inverted at the author.

- Read/increment/write a `u64` at startup, wherever Q1 settles node-scoped
  durable state. There is no existing home: every key in `meta` is prefixed with
  a real shard id or the `SHARD_MAP_PREFIX` sentinel, and a boot counter belongs
  to neither. tk-c593 inherits the same problem for the persisted directory.
- Absent key means first boot: publish at 1. A corrupt one is a warning and a
  restart of the count, not a startup failure.
- Replace `SELF_INCARNATION` in `crates/ggap-node/src/main.rs`.
- Document that wiping the data dir while changing a node's address requires a
  fresh node id (epic Q1: a wiped node restarts low and cannot outbid peers
  holding a higher incarnation).

### Q1 [answered 2026-08-22T06:52:32+00:00] Where does node-scoped durable state live, given every storage key is shard-prefixed?
- a) Reserved sentinel prefix, as ShardMap already uses (SHARD_MAP_PREFIX = u64::MAX) — one established precedent, no change to the hard constraint; needs a second sentinel and a rule about who allocates them
- b) A separate node-scoped keyspace outside meta — honest about the fact that this state has no shard; adds a keyspace and makes the 'all keys are shard-prefixed' constraint conditional
- c) Shard 0's meta namespace — no new concept; false, since a node need not host shard 0, and it silently couples node state to a shard's lifetime
> A separate node-scoped keyspace, not the sentinel. Node facts stop pretending to be shard-prefixed: the boot counter and the directory both live there, keyed by bare label. The directory moves out of meta as part of this — leaving it under the sentinel would put node state in two places, which is the thing this option exists to avoid.

The hard constraint in CLAUDE.md narrows to what it actually protects: all keys in *shard-scoped* keyspaces are prefixed with be_u64(shard_id). The node keyspace is the one exception and is named as such, rather than the constraint being technically-true-via-a-fake-shard-id.

The new keyspace stays in the same fjall Database, so cross-keyspace batches still span it. That matters for the shard map, whose entries are written in the same atomic batch as a split's data movement.

Not settled here: whether the shard map follows. It sits under the same sentinel but is keyed by real shard id and is arguably shard-scoped data. Left where it is for now.

Supersedes the mechanism tk-c593 shipped (keys::NODE_SCOPED plus label-prefix scanning), which was option (a) built before this question was answered. No migration: tk-ef8d Q2 says format-breaking children wipe the data dir.
