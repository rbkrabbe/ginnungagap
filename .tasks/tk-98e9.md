## Context

Epic tk-ef8d Q1 settled the clock that orders a node's descriptors: a boot
counter persisted in the data dir, incremented each start. tk-8978 built
everything that consumes it — `NodeDescriptor.incarnation`, the highest-wins
merge rule, and self-publication each gossip tick — but nothing writes the
counter. `main.rs` passes the constant `SELF_INCARNATION = 1`.

That is correct for a first boot and wrong for every one after it: a node that
restarts at a new address republishes at incarnation 1, which does not outrank
the incarnation-1 copy its peers already hold. The move still converges — the
moved node is the only source re-asserting the new address, the rank-0
membership feed cannot reintroduce the old one above rank 1, and no peer
regenerates it once flipped, so "every peer holds the new address" is the only
absorbing state. But it converges by arrival order rather than by rank, with an
oscillating transient rather than a guarantee.

The transient is longer than it looks. Ties go to the incoming entry, so a
peer's stale copy of the moved node's descriptor overwrites that node's *own*
self-entry in `merge_gossip_state`; `exchange_with` re-snapshots per peer, so
the node can re-emit the stale address about itself to the next peer in the
same round, until `refresh_local` restores it. Sole authorship — the property
the descriptor model exists to provide — is briefly inverted at the author.

- Read/increment/write a `u64` at startup, wherever Q1 settles node-scoped
  durable state. There is no existing home: every key in `meta` is prefixed with
  a real shard id or the `SHARD_MAP_PREFIX` sentinel, and a boot counter belongs
  to neither. tk-c593 inherits the same problem for the persisted directory.
- Absent key means first boot: publish at 1. A corrupt one is a warning and a
  restart of the count, not a startup failure. **Revised by Q2:** a corrupt
  counter recovers from the persisted directory instead of restarting at 1, and
  fails the boot when that record is unreadable as well.
- Replace `SELF_INCARNATION` in `crates/ggap-node/src/main.rs`.
- Document that wiping the data dir while changing a node's address requires a
  fresh node id (epic Q1: a wiped node restarts low and cannot outbid peers
  holding a higher incarnation).

### Q1 [answered 2026-08-22T06:52:32+00:00] Where does node-scoped durable state live, given every storage key is shard-prefixed?
- a) Reserved sentinel prefix, as ShardMap already uses (SHARD_MAP_PREFIX = u64::MAX) — one established precedent, no change to the hard constraint; needs a second sentinel and a rule about who allocates them
- b) A separate node-scoped keyspace outside meta — honest about the fact that this state has no shard; adds a keyspace and makes the 'all keys are shard-prefixed' constraint conditional
- c) Shard 0's meta namespace — no new concept; false, since a node need not host shard 0, and it silently couples node state to a shard's lifetime
> A separate node-scoped keyspace, not the sentinel. Node facts stop pretending to be shard-prefixed: the boot counter and the directory both live there, keyed by bare label. The directory moves out of meta as part of this — leaving it under the sentinel would put node state in two places, which is the thing this option exists to avoid.

The hard constraint in CLAUDE.md narrows to what it actually protects: all keys in *shard-scoped* keyspaces are prefixed with be_u64(shard_id). The node keyspace is the one exception and is named as such, rather than the constraint being technically-true-via-a-fake-shard-id.

The new keyspace stays in the same fjall Database, so cross-keyspace batches still span it. That matters for the shard map, whose entries are written in the same atomic batch as a split's data movement.

Not settled here: whether the shard map follows. It sits under the same sentinel but is keyed by real shard id and is arguably shard-scoped data. Left where it is for now.

Supersedes the mechanism tk-c593 shipped (keys::NODE_SCOPED plus label-prefix scanning), which was option (a) built before this question was answered. No migration: tk-ef8d Q2 says format-breaking children wipe the data dir.

### Q2 [answered 2026-08-22T09:37:42+00:00] A corrupt boot counter restarts at 1, which permanently inverts authorship rather than merely losing an ordering guarantee. What should a corrupt counter do?
- a) Restart at 1 with a warning — never fails a boot; the node can never win its own address back, and re-emits the stale one
- b) Floor the count from the persisted directory's self-entry; fail the boot if that record is unusable too — recovers the rank whenever the two records did not rot together, and refuses to start rather than start unrankable
- c) Fail the boot on any corrupt counter — simplest rule, but turns a lost cache into an outage when the rank was recoverable
> Floor the count from the persisted directory, and fail startup if that fails too. A *missing* counter keeps meaning first boot — the floor is only for a counter that is present but unusable. A missing or self-less directory under a corrupt counter also means first boot; only a directory record that is present and unreadable fails the boot.

Rationale: a corrupt counter is not the same as a wiped data dir. The wipe has no remedy — the bytes are gone. The corrupt counter does: the persisted directory is a separate key in the same node keyspace and its self-entry carries the incarnation this node last published. Flooring at that + 1 repairs the rank whenever the two records did not rot together, and the normal path is untouched because a readable counter always wins.

Starting unrankable is worse than not starting: the node cannot correct its own address, refresh_local loses the tie every tick, and exchange_with re-snapshots per peer so it re-emits the stale address about itself. That is an outage that looks like a healthy node.

Supersedes the tk-98e9 acceptance line 'an absent or corrupt counter starts at 1 with a warning, never a failure' — absent still does; corrupt no longer does. Absorbs tk-3107.

## Notes from implementation

**The inversion is permanent, not transient.** The Context above describes a
node publishing below its peers' rank as an oscillating transient. That is true
only for a *tie*. Below the rank it is absorbing: `refresh_local` re-merges the
self-entry at the same losing incarnation every tick, so it loses the same
comparison forever, and `exchange_with` re-snapshots the registry per peer while
`refresh_local` runs once per round — so the node forwards the stale address
about itself to the remaining peers in that same round. It cannot recover, and
it reports healthy throughout. This is what turned Q2 from a preference into a
correctness question.

**An absent counter must not consult the directory.** A node re-seeded by its
peers before it ever published has a directory entry it did not write. Flooring
from it would let the node adopt a rank it never held — inventing a history
rather than recovering one. Only a counter that is present and unusable gets the
fallback.

**`DirectoryStore::load` is deliberately infallible**, so it cannot tell absent
from corrupt. The recovery needs that distinction (first boot vs unrankable),
hence `try_load`; `load` stays a warning-and-empty wrapper over it, so no
existing caller changes behaviour.

**A failed counter *write* stays a warning.** This boot is correctly ranked; only
the next one re-uses the incarnation, and a tie goes to the incoming entry — so
the self-publication takes it back on the following tick. A deficit is fatal, a
tie is not.

**`cargo test` fails fast across targets.** A mutation that broke both the
storage unit tests and the consensus integration test showed only the consensus
failure, because cargo stops at the first failing target. `--no-fail-fast` is
needed to confirm which levels actually catch a mutation — without it a coverage
claim about the other targets is unfounded.
