## Context

Per Q2, this is persistence only — no `--join` flag.

The reason the flag is not needed: a joining node is *dialled*, it never dials.
`main.rs:264` leaves a non-seed fresh node's Raft uninitialized until the leader
sends it AppendEntries after `AddLearner`, and `gossip_service.rs:22` returns
the responder's full view, so one inbound `Exchange` hands a new node the entire
directory. Peers re-seed a restarted node the same way within a gossip round.

So persistence buys *immediacy*, not capability: a node that restarts and is
elected before any peer has gossiped to it can resolve its peers straight away
rather than failing sends until someone dials it. That is the case to test.

Store it in the `meta` keyspace alongside the other node-scoped keys. It is a
cache of gossip, so a corrupt or absent record must be a warning and an empty
directory, never a startup failure — the node recovers by being dialled.

`seed_peers` stays exactly as it is, and its scope narrows to what actually
needs it: nodes in no membership that nobody will ever dial — the observer
harness, and later `ggap-pd`. Close tk-9bcd with that reasoning rather than
adding the CLI flag it proposed.

## Notes from implementation

- **The node-scoped `meta` namespace was not actually namespaced.** `ShardMap`
  owned the `u64::MAX` sentinel outright and `load` prefix-scanned the bare
  sentinel, so any second node-scoped key would be read back as a `ShardInfo`
  and fail the decode — a hard startup failure, from adding an unrelated record.
  Fixed here rather than worked around: the sentinel moved to `keys::NODE_SCOPED`
  as shared ground, and `ShardMap` scans `meta_key(NODE_SCOPED, "shard:")`.
  A test in `directory.rs` pins that the shard map ignores the directory record.
- **Persisting after the exchange, not after `refresh_local`.** A round can learn
  entries from the peer it dialled, and those are exactly the ones worth having
  on the next boot. Skipping the write when the snapshot is unchanged keeps a
  steady-state cluster from writing every second.
- **Incarnations are persisted with the entries**, so a restored entry still
  outbids the stale copies in flight. Restoring at incarnation 0 would have
  quietly inverted that; it has its own test.
- The gossip task writes; the registry stays a pure in-memory cache with no
  storage handle. `ggap-node` seeds the registry from the same store before
  starting the task, which is the sequence the tests exercise.
- Discovered: tk-c47e (nothing removes a departed node from the directory, and
  persistence removes the whole-cluster-bounce escape hatch).
