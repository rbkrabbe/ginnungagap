## Context

Per Q2, this is persistence only — no `--join` flag.

The reason the flag is not needed: a joining node is *dialled*, it never dials.
`main.rs:264` leaves a non-seed fresh node's Raft uninitialized until the leader
sends it AppendEntries after `AddLearner`, and `gossip_service.rs:22` returns
the responder's full view, so one inbound `Exchange` hands a new node the entire
directory. Peers re-seed a restarted node the same way within a gossip round.

So persistence buys *immediacy*, not capability: a node that restarts and is
elected before any peer has gossiped to it can resolve its peers straight away
rather than failing sends until someone dials it. That is the case to test.

Store it in the `meta` keyspace alongside the other node-scoped keys. It is a
cache of gossip, so a corrupt or absent record must be a warning and an empty
directory, never a startup failure — the node recovers by being dialled.

`seed_peers` stays exactly as it is, and its scope narrows to what actually
needs it: nodes in no membership that nobody will ever dial — the observer
harness, and later `ggap-pd`. Close tk-9bcd with that reasoning rather than
adding the CLI flag it proposed.
