## Context

`BootCounter::write` (`boot_counter.rs`) persists the rank with a bare
`store.node.insert`, with no persist or fsync. tk-d4b8 made a *failed* write
fatal, which closes the route where the keyspace reports an error — it does
not close the route where the write is acknowledged and then lost to power
loss before it reaches disk. The next boot then reads the stale counter and
reissues the rank the previous boot already published at.

tk-d4b8 also made an equal rank keep the entry already held, so that case no
longer self-heals by arrival order: a node that moved across such a crash
publishes at a rank its peers already hold for the old address, and the move
never installs. The uniqueness property the ordering rule rests on is
therefore enforced against API errors but not against crashes.

Narrow but not theoretical: the window is one boot, and it needs a crash
between the counter write and the disk.

**The API question is answered** (2026-10-11), so this is no longer a
research task. `fjall::Database::persist(PersistMode)` exists
(`fjall-3.0.3/src/db.rs:353`) with `SyncData` (`fdatasync`) and `SyncAll`
(`fsync`). One call after the counter write, once per process start, is the
whole cost — not something that needs weighing.

**A second route, same consequence.** `boot_counter.rs:149-170`
(`recover_from_directory`) rebuilds the rank from the persisted directory when
the counter is unusable. The directory is written by the gossip task, so it
lags: a node whose counter rots before that task has persisted this boot's
self-entry recovers a rank it has already published at, and reissues it. No
fsync fixes that one — it is a liveness gap between two records, not a
durability gap in one. Both routes end in the same place, so they belong in
one task.

**Severity comes from tk-d4b8.** Before ties-lose, a reissued rank produced a
flap that arrival order eventually resolved; now it is permanent
non-adoption and permanent loss of self-authorship. The two tasks are
coupled: tk-d4b8 traded a recoverable failure for an unrecoverable one in
exchange for closing the reinstatement vector, sanctioned by its Q1.

### Q1 [answered 2026-10-12T07:38:53+00:00] recover_from_directory rebuilds the rank from a record the gossip task writes, so it lags this boot's own publication. fsync does not help. What closes it?
- a) Persist the directory immediately after the first self-publication, so the record the fallback reads is never behind by more than a tick — small, and keeps the fallback as-is
- b) Add a margin to a recovered rank (recovered + N rather than + 1), so a lagging record still yields a rank above anything published from it — no new write, but it burns incarnations and the margin is a guess
- c) Drop the directory fallback entirely and fail the boot when the counter is unusable — simplest and never wrong, but turns a recoverable counter corruption into an outage needing a fresh node id
> c) Drop the directory fallback and fail the boot when the counter is unusable. A corrupt key is not a condition to recover from — it means something is wrong that recovering would hide. The payoff is bigger than closing the lag route: with the fallback gone and the write made durable, rank uniqueness becomes flatly true again rather than true-with-a-window. Counter readable means a unique rank, absent means a first boot at 1, corrupt means no boot at all; and the fsync closes the acknowledged-then-lost route. That flat claim is what tk-d4b8's tie rule is justified by, and it is currently asserted without the caveat it needs — so this removes the need for the caveat instead of adding one. Operator cost, which the error must name: a corrupt counter needs a fresh node id, because wiping the data dir restarts the count at 1 and loses to the ranks peers already hold. Route 1's durability goes behind a FjallStore method rather than a raw db.persist from boot_counter.rs: fjall's API is confined to fjall.rs today and boot_counter names none of it, so PersistMode stays in one place.

## Outcome (2026-10-12)

Both routes closed, and the point of closing them is that the *claim* becomes
true: counter readable means a unique rank, absent means a first boot at 1,
unreadable means no boot at all, and the write is flushed to disk. There is no
window left, so `boot_counter.rs` and `docs/ggap-storage.md` keep asserting
uniqueness flatly — which they already did, slightly ahead of the facts, and
which tk-d4b8's tie rule needs.

**Durability sits behind the storage layer.** `FjallStore::sync_to_disk` is the
one place that names `fjall::PersistMode`; `BootCounter` asks for durability in
domain terms. `boot_counter.rs` named no fjall API before this and still names
none — reaching for `store.db.persist` would have put fjall's surface in a
second file, and `store.db` is otherwise touched only by `fjall.rs`.

**`recover_from_directory` is deleted**, along with six unit tests that pinned
it and one integration test. The integration test is replaced rather than
dropped: it now plants a directory that *would* have served a fallback and
asserts the boot fails anyway, which is the only version of that test that
says something now.

`DirectoryStore::try_load` became dead public API with the fallback — it was
public solely so the counter could tell a first boot from an unrankable one.
Now private, with its own doc saying why it still exists at all (`load` is
built on it).
