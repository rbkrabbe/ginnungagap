## Context

A node that retires itself calls `std::process::exit(0)`
(`ggap-node/src/main.rs`, the task spawned on the retire token). Under a
supervisor that is not an ending — it is a restart.

`deploy/k8s/ggap/statefulset.yaml` runs 3 replicas, and a StatefulSet pod may
only have `restartPolicy: Always`. So the real sequence is: retire, exit 0,
kubelet restarts the container, the boot guard reads the self-tombstone
tk-8c62 persisted, `bail!` exits non-zero, **CrashLoopBackOff** — for as long
as the pod exists.

And it exists for a while: scaling a StatefulSet down removes the *highest
ordinal*, so a retired middle node cannot be removed by scaling at all without
taking healthy nodes with it. There is no operator step that tidies this up.

## Shape

Stop serving and stay up, rather than exiting:

- The client KV API stops answering.
- Gossip keeps running, so the tombstone keeps propagating to peers that were
  unreachable when `RemoveNode` ran — today propagation stops dead at the
  exit, leaving it to whichever peers took the broadcast.
- The process idles until an operator removes the pod.

What this simplifies, beyond the crash loop: `do_remove_node`'s two `retire`
call sites currently need different failure handling, because the self-retire
path is past a point of no return it cannot report from — it logs an error and
exits anyway (tk-8c62). A node that stays up can let the next gossip round
persist a failed write, exactly as the on-behalf path does, and the two
branches converge. The 500ms sleep that gives the RPC response time to escape
goes with it.

tk-8c62's write-through is still needed: the boot guard reads that record, and
a pod can be rescheduled without ever passing through `RemoveNode`.

## The wrinkle

"Stop listening" is not listener-granular. `GossipService.Exchange` is served
on the **cluster** listener alongside Raft and Admin (`ggap-server/src/lib.rs`
registers all three together), and gossip is the one thing that must keep
running. Q1 settles it with a layer over the other three rather than by
stopping anything.

## Two ways in, one state

The retired state is reached both by the running node and by a restart of it,
and must mean the same thing in each:

- **At runtime**, the retire token `RemoveNode` already cancels sets the flag,
  instead of exiting the process. The 500ms sleep that gave the response time
  to escape goes with the exit, and a failed persist stops being terminal —
  the node is still running, so its next gossip round writes the tombstone,
  exactly as the on-behalf path relies on.
- **At startup**, the boot guard at `main.rs` stops `bail!`-ing and sets the
  same flag. A node whose own entry is a tombstone comes up quiesced instead
  of refusing to start, which is what removes the CrashLoopBackOff rather than
  merely deferring it: a pod rescheduled for any reason — drain, OOM, node
  failure — would otherwise hit the guard and loop. At startup it can go
  further than the layer and not register the three services at all, nor start
  its Raft groups.

Quiescing is safe because a tombstone is absolute in `merge_directory`:
`refresh_local` publishes this node's own descriptor every tick, loses to its
own tombstone locally, and so the node gossips the removal rather than its
address. A quiesced node cannot re-announce itself.

Also worth doing while here, and cheap: shut the local Raft groups down on
retirement rather than leaving them running against nobody, and surface the
retired state on the **metrics** endpoint, which is on neither gRPC listener
and so is unaffected. Without that last part a quiesced pod is
indistinguishable from a healthy one — it passes its liveness probe, holds its
PVC and keeps its ordinal.

### Q1 [answered 2026-10-11T14:30:52+00:00] Gossip must keep serving while KV, Admin and Raft must not, and all four share two listeners. How is that expressed?
- a) Gate per service — a retired flag the KV, Admin and Raft services check, answering UNAVAILABLE. No listener surgery, needs nothing from tk-bf4e, but adds a check to every service and leaves the ports open
- b) Split the listeners — move gossip onto its own, so retiring can drop the client and cluster listeners outright. Cleanest shutdown story, but a third port to configure, document and expose in k8s, and it needs tk-bf4e for the drop
- c) Drop the client listener, gate the cluster one — KV stops at the listener (tk-bf4e), while Admin and Raft are gated in place beside gossip. Mixed, but matches where the risk is: the KV API is the one serving clients
> Neither per-method gating nor listener surgery: a tower layer wrapping the KV, Admin and Raft services that fails fast while a retired flag is set, with Gossip left unlayered. The flag is set two ways and the state is identical in both — at startup, after reading a self-tombstone from the persisted directory, and at runtime by the retire token RemoveNode already cancels. Per *service* rather than per method, so every existing and future method of those three is covered without anyone remembering to add a check; registering a genuinely new service is a deliberate act at the same site the layer lives. Needs nothing from tk-bf4e, since nothing is stopped — the ports stay open and answer UNAVAILABLE, which also beats connection-refused for diagnosing an idle pod. Rejected: a flag read inside each method (allow-by-default, so the next endpoint added is silently ungated), and splitting gossip onto its own listener (a third port to configure, document and expose for no gain once the layer exists). At startup the node can go further than the layer and simply not register the three services at all, nor start its Raft groups, since the state is known at main.rs:273 and nothing serves until :487.

## Outcome (2026-10-11)

`retired_gate` in `ggap-server/src/lib.rs` wraps `KvService`, `AdminService`
and `RaftService` in `InterceptedService`, answering `UNAVAILABLE` while the
token is cancelled; `GossipService` is left unwrapped. Six wrap sites, because
each of the four `serve_*` functions registers its own services. The token is
the `CancellationToken` that already existed on `ClusterServiceConfig` as the
signal *out* of `RemoveNode`; `KvServiceConfig` gains the same field.

`ggap-node` sets it from both routes — `RemoveNode` as before, and the boot
guard, which now logs and cancels instead of `bail!`-ing — and starts no Raft
group when it is set. The exit, and the 500ms sleep that gave the RPC response
time to escape it, are gone.

Tested over real gRPC rather than in-process, since an in-process call never
touches the interceptor. Both halves are mutation-checked: making the gate
ignore the flag fails at the KV assertion, and gating gossip too fails at the
gossip assertion.

### What review caught, and it was the main thing

**Removing the exit left every background task running forever.** The exit
used to bound them to 500ms. The runtime handler only logged, so after
`RemoveNode` the Raft groups, each shard's `TtlGcTask` and its
`ttl_rx -> client_write` loop, and `RaftMetricsTask` all kept going for the
pod's lifetime — while `docs/ggap-node.md` and CLAUDE.md both said "no Raft
group runs", which was true of the boot path only.

The sharp consequence was not the wasted work. `GossipTask::refresh_local`
keeps `upsert_local`-ing a `ShardEntry` for every shard in the router, with
`version` rising each tick; `merge_entry` orders on `(term, version,
leader_origin)` with **no tombstone check**, so at equal term a retired node's
ever-rising version wins at every peer — and that is the view `AdminService`
answers `ClusterStatus` from for a shard it does not host. A retired node
would have gone on overwriting the live view of a shard it no longer hosted.

This is what the Shape section asked for ("shut the local Raft groups down on
retirement rather than leaving them running against nobody") and it was simply
not done — not deferred, not recorded. Fixed by hanging Raft, TTL GC and the
metrics tasks off a `shard_tasks` token that is a child of `shutdown`, so
retirement cancels them while gossip — a child of `shutdown` directly —
survives; and by dropping the shards from the router, which is what stops
`refresh_local` publishing for them.

Also fixed: five comments in `admin_service.rs` and one in `lib.rs` still
described the exit, the test rationale for
`a_self_retiring_node_persists_its_own_tombstone_before_answering` was built
on it, and the retire log line still said "shutting down" — which
`docs/ggap-node.md` told operators to read to identify a quiesced pod.

Two consequences worth their own tasks rather than a silent decision here:
tk-1dfe (the delivery precondition's premise is gone, since a quiesced node
would deliver the tombstone eventually) and tk-d08b (the two failure paths can
now be one).

### The sweep that kept missing one line

`directory_persistence.rs` justified `retire`'s write-through with "the node
retiring itself exits before another round can happen" — a comment written
earlier in this same session, under tk-8c62, and false the moment the exit
went. Two sweeps missed it, both times because they searched the *files this
change had edited* rather than the *behaviour it had removed*.

Sweeping by behaviour instead — grepping for the premise ("about to stop",
"moments later", "dies with it") rather than for the files — found two more
that both earlier passes and the review had left: `registry.rs`'s `retire`
body and `gossip.rs`'s `broadcast_removal` doc, plus one in
`docs/ggap-consensus.md`. All three had the same shape: a true conclusion
resting on a dead premise.

The conclusion was never wrong, which is why it survived three readings —
nothing re-derives a removal, and a node can lose its process without passing
through `RemoveNode` at all, so the write still cannot wait for a round. Only
the reason had to change.

A fourth round with the reviewer's own search terms (`about to exit`,
`vanish with the process`, `before it stops`) found **six more**, including the
`DirectoryStore` module doc — the canonical place a reader looks the rule up,
in a file this change never touched — and the operator-facing refusal message
in `do_remove_node`, which still told them the removal "would be lost when it
stops". Also `boot_counter.rs`'s test doc, which claimed a retired node "never
gets that far": `advance` runs before the tombstone is read, so it does, and
is harmless for a different reason than the one written.

Twelve sites in total, five rounds, four different search vocabularies — the
last found in the same file as one fixed in the same round, 56 lines apart. The
lesson is not "sweep harder" — it is that removing a behaviour leaves its
justification scattered through files the change does not touch, and only a
search for the *premise* reaches them. A diff-scoped review cannot.

### Two things deliberately not done

- **The two `retire` failure paths are not merged.** Not exiting removes the
  reason they differed — the self-retire path is no longer past a point of no
  return it cannot report from — so the error-log-and-continue in
  `admin_service.rs` could now be the same code as the on-behalf warning. Left
  alone because it is a behaviour-neutral tidy-up in a file this change
  otherwise does not touch, and worth its own small edit rather than riding
  along here.
- ~~**No new metric for the retired state.**~~ Reversed. The first attempt
  ticked the visibility box while recording that no metric existed, which
  review correctly called self-contradicting — and worse after finding 1's
  fix, since cancelling `RaftMetricsTask` freezes the `raft_*` gauges and
  makes a retired node scrape identically to an idle healthy one. `metrics`
  was already a dependency and the facade is one line, so
  `ggap_node_retired` is now set at startup and on retirement. tk-09bb, filed
  to do this later, is dropped as done here.

### Not addressed, and still true

A quiesced pod passes its liveness probe, holds its PVC and keeps its ordinal,
so a cluster with one retired node still looks like N nodes to Kubernetes.
That is inherent to not exiting and is the cost of the choice, not an
oversight — `docs/ggap-node.md` says so under "A retired node".
