## Context

Where the compensation gets deleted.

`refresh_local` (gossip.rs:179-233) currently does two things with addresses:
seeds this node's own entry from config, then merges membership as *cluster-only*
entries because membership had no client address to give. After tk-fd58 it does,
so both halves collapse into one: derive the full entry from `raft.metrics()`.

- Delete the self-seed. A node's own entry arrives through membership like
  everyone else's, which also removes the "originated by exactly one node"
  property that made the whole thing fragile.
- `merge_directory`'s field-wise rule and the empty-means-unknown convention were
  scaffolding for that asymmetry. Re-examine both — this child should be able to
  simplify the merge, not just feed it better data. If the field-wise rule
  survives, say why in the task.
- `GossipTask::new`'s `self_client_addr` parameter goes away, and with it the
  seeding in `ShardRegistry::new` at main.rs and in every test harness.
- tk-7664 (a node hosting no shards never publishes itself) may be resolved or
  made moot here — check it rather than leaving it stranded.

## The merge rule

The field-wise rule is gone. `merge_directory` now replaces whole values, and
"empty" is no longer a meaningful state to merge around.

Why it could go: field-wise merging existed because two feeds each knew half a
node — membership knew the cluster address, the self-seed knew the client
address — and neither could be allowed to blank the other's half. After tk-fd58
and tk-d049 there is one feed. A directory entry is a copy of one membership
record, and its two fields belong together.

What that buys beyond simplicity: a member with no client address can now say
so. Under the field-wise rule an absent client address was indistinguishable
from "unknown, don't touch it", so a stale one could never be retracted.
Whole-value replacement makes the absence a fact that propagates.

**The invariant is about provenance, not content.** An earlier draft of this
section claimed "every path into consensus state carries a full `NodeAddrs`".
That is true of production paths only — bootstrap and a split's `source_members`
carry both, and `AddLearner` rejects an empty `client_addr` — but *not* of the
repo as a whole: `rpc_metrics.rs`, `trace_propagation.rs`, `kv_write.rs` and
`raft_metrics_task.rs` all initialise membership via `GgapNode::cluster_only`.
Attach a `GossipTask` to one of those and the directory will report no client
address for those members. Under the new rule that is correct — membership
really does not carry one — where the old rule would have reported an address
consensus never held. The rule the merge depends on is only that every entry
*comes from* membership, which is why keeping seeds out of the directory is the
load-bearing part.

The one remaining source that knows only a cluster address is a bootstrap dial
hint, and that is exactly why it is no longer a directory entry:
`ShardRegistry::new` takes `seed_peers: (node_id, cluster_addr)` into a separate
field that `peers_excluding_self` unions in and `snapshot_for_gossip` never
emits. A seed can therefore never be gossiped over a fully-known entry. That
keeps the invariant total — **every directory entry comes from a committed Raft
membership** — which is what makes whole-value merging safe.

Ordering between two full entries is still last-write-wins; tk-c4fc adds the
membership `(term, index)` stamp. Note that removing the self-seed removes the
per-tick self-repair that tk-1bf0 observed papering over stale copies, so
tk-c4fc matters more now, not less.

Skipping empty fields is the field-wise rule under another name; it would reinstate the 'absent means unknown, do not touch' conflation and make a stale client address unretractable, which is the defect the change exists to remove. NodeAddrs::cluster_only and GgapNode::cluster_only are first-class constructors, so an absent client address is a representable fact, not an error state to defend against. Narrowing the invariant from content to provenance is the right fix, and the task file does it honestly — it names the earlier draft as wrong, lists the four cluster_only sites, and states the production-paths-only caveat.
