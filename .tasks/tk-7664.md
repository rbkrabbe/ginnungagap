## Context

`refresh_local` returns early when `router.local_shard_ids()` is empty (gossip.rs:98-100), which skips both the self-seed and the membership-derived directory merge. A node hosting no shards therefore never refreshes its own directory entry and never learns peers from Raft membership.

Harmless today: every node hosts shard 0, and `ggap-node` seeds self into the registry at construction, so the entry exists even if never refreshed. It becomes real the first time a node can legitimately host zero shards — after rebalancing, or a drained node awaiting placement — at which point that node also stops gossiping entirely (`peers_excluding_self` stays empty), so it goes blind rather than degrading.

Noticed while reasoning about where client_addr is originated in tk-c507; deliberately not fixed there, since it predates that change and has its own failure mode.

Fix is probably to hoist the self-seed above the early return, and to reconsider whether the early return should gate the exchange round at all.

## Resolution (tk-11b6)

There is no self-seed left to hoist. The directory is derived entirely from
Raft membership, so a node hosting no shards has nothing to publish about
itself — and nothing *should* publish it, because it is in no shard's
membership and no peer needs to route to it.

The early return in `refresh_local` was never the thing that gated gossip:
`run` calls `exchange_round` unconditionally, so a shardless node still trades
directories with its peers and learns the cluster. What it lacked was a peer
address to start from, and that is now an explicit bootstrap seed
(`ShardRegistry::new`'s `seed_peers`) rather than a side effect of self-seeding
— which is what the observer harness in `three_node_cluster.rs` uses.

The remaining half of the original worry — a drained node needing to be
reachable while it awaits placement — is a placement-driver concern
(`ggap-pd`), not a gossip one.
