## Context

tk-19c0 made `BootCounter::write` flush the rank to disk, and
`a_flush_failure_refuses_the_boot_and_leaves_the_rank_written` pins what
happens when that flush *fails*. Nothing pins that it is called at all:
replacing `self.store.sync_to_disk()` with `Ok(())` in
`crates/ggap-storage/src/boot_counter.rs` leaves the entire suite green
(verified during review).

So the uniqueness property tk-19c0 established — and which tk-d4b8's tie rule
rests on — can be silently weakened back to where it was by deleting one line.
Everything downstream keeps asserting uniqueness flatly, in
`boot_counter.rs`, `docs/ggap-storage.md` and CLAUDE.md.

## Why it was left

Pinning the call needs either a spy at the `FjallStore` boundary (a counter
incremented by `sync_to_disk`, exposed under `test-utils`) or a crash
harness that kills the process between the insert and the flush and reopens.
The first is small but puts test-only state on a production type; the second
is real machinery. Neither fits in the `s` that tk-19c0 was.

## Shape

The spy is the proportionate option: `FjallStore` already carries
`crash_after_phase1` for the state machine under the same gate, so a
`syncs_performed()` counter is a pattern the crate has. A test then asserts
that one `advance` performs one flush — which fails if the call is deleted,
and does not care how fjall implements it.

Rejected unless someone wants it: asserting through a reopen. The existing
test's "next boot" is a new `BootCounter` over the same live handle, so it
reads the keyspace rather than the disk; a reopen would not distinguish
flushed from unflushed either, since the OS buffer serves the read.
