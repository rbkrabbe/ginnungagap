## Context

tk-ef8d's goal is one sentence: an operator changes a node's address by
restarting it with a new `--cluster-addr` / `--client-addr`, and the cluster
follows. The epic's adversarial review found that scenario covered in three
separately-verified halves and never composed:

- `ggap-consensus/tests/boot_incarnation.rs` uses real `FjallStore` reopens and
  the real `BootCounter`, but merges into bare registries with no Raft.
- `network.rs:409` proves a single client re-dials a moved target against a
  live server.
- `ggap-server/tests/three_node_cluster.rs` proves addresses are resolved from
  the directory.

Nothing restarts a member of a *running* Raft cluster at a new address and
shows replication resume. Every mechanism the epic built is exercised; the
thing they were built for is not.

## Blast radius

`crates/ggap-server/tests/three_node_cluster.rs` most likely — it already
builds nodes on pre-bound listeners and holds `advertised_client_addr`, so a
restart-at-a-new-address harness is an extension of what is there rather than a
new fixture. Check whether a node can be torn down and rebuilt on the same data
dir with different listeners without disturbing the other two.

## Acceptance

- [x] A three-node cluster restarts one member at a new cluster address, and
      the other two resume replicating to it without a process restart of
      their own.
- [x] The moved node is reachable by node id through the directory afterwards,
      with no address anywhere in membership — asserted on the encoded
      membership, scanned for both the old and the new address. The first
      version compared each `GgapNode` to `GgapNode {}`, which is field-less
      and so true by construction; the review caught it.
- [x] The test fails if resolution is cached per node id rather than per
      address — verified by mutating `needs_redial` to ignore the address:
      the moved node never receives the post-move write.
- [ ] ~~The test fails if the boot counter stops advancing~~ — **not
      achievable until tk-d4b8 is decided.** Mutating `BootCounter::advance`
      to a constant 1 leaves the test green: `merge_directory` gives ties to
      the incoming entry, so a descriptor at a rank peers already hold still
      wins on arrival and the move succeeds anyway. Recorded on tk-d4b8, which
      should pin this case when it lands.
- [x] Full checklist green: fmt, clippy -D warnings, build, test.

## Outcome (2026-10-09)

`a_restarted_member_at_a_new_address_rejoins_the_cluster` in
`three_node_cluster.rs`, plus two harness changes it needed:

- `start_node` now restores the persisted directory into the registry before
  Raft starts, and gives the gossip task a `DirectoryStore`. The harness did
  neither, so test nodes never persisted a directory and a restarted one came
  up unable to resolve any peer — while `ggap-node` has done both since
  tk-c593. Worth noting on its own: every directory-persistence assertion in
  this file was previously vacuous.
- The split handler is held in `_handles` rather than spawned detached, so a
  restart can drop its store clone.

Review found two defects, both fixed:

- The membership assertion was a type-level tautology (above). Replaced with
  the byte scan already used by `replicated_membership_carries_no_address`.
  Verified by positive control, not by inversion: inverting an assertion makes
  it fail whatever the bytes are, so it proved only reachability. Giving
  `GgapNode` an address field and having the harness bootstrap carry it turns
  the scan red naming the address. Noted there too: the encoded membership is
  13 bytes against a 15-byte needle, so in a clean build the window iterator
  is empty and the pass is a length result rather than a content one — sound,
  weaker than it looks, and filed as tk-cf14 for both loops.
- `.tasks/tk-5a4b.md` had been flipped to `done` in this working tree. That
  task's code is on its own branch and PR, so on this branch the comments it
  names are untouched while its file claimed otherwise. Reverted here; the
  status belongs to that branch's commit.

One step is unfaithful and could not be made otherwise: storage is handed to
the replacement node as a live `Arc<FjallStore>` rather than closed and
reopened. `ggap-server`'s serve functions take no shutdown hook, so a test can
only abort the server future, and tonic's per-connection tasks outlive that
holding a store clone — measured still `Locked` 15 s after shutdown with peers
connected. Filed as tk-bf4e; `boot_incarnation.rs` already covers the genuine
reopen in isolation.

### Q1 [answered 2026-10-09T18:23:01+00:00] Should this test be upgraded to a true close-and-reopen once tk-bf4e lands?
- a) Yes — tk-bf4e makes it possible, and a restart that does not reopen its own data dir is not quite the operator action the epic describes. Costs a revisit of a passing test.
- b) No — the handover already preserves id, log, state machine and boot counter, and `boot_incarnation.rs` covers the reopen against real fjall. Leaves one documented gap between the test and the thing it models, forever.
