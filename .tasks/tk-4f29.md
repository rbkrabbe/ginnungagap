## Problem

A write or linearizable read that lands on a follower fails with UNAVAILABLE and
a leader hint the caller cannot act on. This makes it succeed: the receiving node
forwards it once to the shard leader and returns the leader's response.

## Approach

A LeaderForwarder component in ggap-server: resolve the leader for the routed
shard from ShardRegistry (lookup(shard).leader_id -> directory client_addr),
dial it over a cached channel, replay the request once with a ggap-forwarded
marker, return the response verbatim.

Transport is the leader's *client* port, learned from a new client_addr field
gossiped alongside cluster_addr (tk-3846 Q7). Rejected: serving KvService on the
cluster listener (Q1's original answer) — it would put forwarded client traffic
on the same listener as Raft, so a client-load spike delays AppendEntries and can
trigger spurious elections.

Loop prevention is the ggap-forwarded metadata marker and nothing else (Q4). A
receiver that sees it serves or fails but never forwards again. Rejected: a hop
path list, which reopens the Q2 fail-fast decision and spends the caller's
deadline across hops with no budget.

Leader unknown or moved mid-forward: fail fast with UNAVAILABLE plus the hint,
no server-side retry (Q2).

## Changes

- proto/ginnungagap/v1/cluster.proto — GossipNode gains client_addr.
- crates/ggap-consensus/src/registry.rs + gossip.rs — directory holds
  (cluster_addr, client_addr); new accessor for the client addr; merge and
  snapshot carry it. Empty client_addr is ignored like an empty cluster_addr.
- crates/ggap-server/src/forward.rs (new) — LeaderForwarder: resolve, cached
  channel per node id (mirroring the lazy pattern at network.rs:71), replay once,
  set the marker, propagate deadline and trace context.
- crates/ggap-server/src/kv_service.rs — do_put, do_delete, do_compare_and_swap,
  and the linearizable paths of do_get and do_scan forward on NotLeader when the
  request is not already marked. Watch is untouched (Q3).
- crates/ggap-node/src/main.rs + ggap-server/src/lib.rs — construct the
  forwarder, thread the registry and this node's client_addr into KvServiceImpl.

## Out of scope

- Watch (Q3) — proxying a long-lived server stream is its own task.
- AdminService forwarding (Q8) — replaced by the console proxy, tk-f7b6.
- Multi-hop forwarding and any server-side retry loop (Q2, Q4).
- Serving KvService on the cluster listener (Q7).

## Acceptance

- [ ] A write sent to a follower succeeds, and the value is readable on the leader.
- [ ] A linearizable read sent to a follower returns the committed value.
- [ ] A request arriving with ggap-forwarded set is never forwarded again: a
      follower that receives one returns NotLeader rather than bouncing it.
- [ ] With the leader's entry absent from the registry, the request fails fast
      with UNAVAILABLE and a hint — no retry loop, no hang.
- [ ] Forwarded requests are distinguishable from locally-served ones in metrics
      or traces.
- [ ] Repeated forwarded requests reuse one channel per target rather than
      dialling per request.
- [ ] Watch still serves locally and is unaffected.
- [ ] Full checklist green: fmt, clippy -D warnings, build, test.

## Risks

- Registry staleness: leader_id comes from gossip, so a just-elected leader may
  be missing or wrong. Fail-fast (Q2) makes this a visible retry rather than a
  hang, but the test above must cover the empty-entry case explicitly.
- client_addr is a new gossiped field; a mixed-version cluster gossips empty
  strings for it. Treat empty as unknown and fail fast, never dial "".
- kv_service.rs is 519 lines and five call sites change; the forward decision
  belongs in one shared helper, not copied per method.

### Q2 [answered 2026-07-30T08:11:31+00:00] do_scan hops across up to MAX_SCAN_HOPS_PER_RPC (8) shards in one RPC. If a later hop returns NotLeader after earlier hops already collected entries, what happens?
- a) Forward only on the first hop — if entries are already collected, return the partial page plus a continuation token (an already-legal response) and let the client resume, landing the retry on the right shard
- b) Forward the whole ScanRequest — that leader may not host the earlier shards, so it re-routes by key and redoes hops 1-2
- c) Do not forward Scan at all — smallest change, but the console KV browser lists keys via Scan so the epic goal stays unmet
> Forward only on the first hop. With entries already collected, stop and return the partial page with a continuation token; the client's resume lands on the correct shard by key. Forwarding a partially-executed multi-shard scan would re-execute it at a node that never saw the original cursor.
