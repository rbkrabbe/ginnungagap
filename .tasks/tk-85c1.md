## Context

ensure_linearizable_or_lease() in crates/ggap-consensus/src/node.rs:104-107 maps every openraft error — including ForwardToLeader — to GgapError::Consensus. So a linearizable read/scan served by a follower surfaces as gRPC INTERNAL ("consensus error: has to forward request to: Some(3), Some(BasicNode { addr: ... }))") instead of GgapError::NotLeader, which convert.rs:46 turns into UNAVAILABLE plus the ggap-leader-addr metadata hint.

Every other openraft call site already does the forward_to_leader() check: add_learner (node.rs:150), change_membership (node.rs:178), propose (node.rs:214), split.rs:150. This one call site is the outlier.

Reported from the console KV browser hitting a follower node.

Fix: mirror the existing pattern in the map_err. Regression test in crates/ggap-server/tests/three_node_cluster.rs asserting a linearizable read against a follower returns NotLeader with a leader address hint (mirrors the existing add_learner-on-follower test at :619).
