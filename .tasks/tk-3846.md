## Context

The console KV browser reaches the cluster through a NodePort, so it lands on whichever node the service picks. Writes and linearizable reads that land on a follower fail with ForwardToLeader. The client cannot follow the leader hint itself: the addr openraft reports is an in-cluster DNS name (ggap-2.ggap-headless.ginnungagap.svc.cluster.local:17001) that a browser outside the cluster cannot resolve. Human decided the fix is server-side forwarding rather than a topology-aware proxy.

Shape: when ShardRouter/OpenRaftNode returns GgapError::NotLeader, KvServiceImpl proxies the request to the leader over the cluster network and returns the leader's response to the client, instead of surfacing the error.

Constraint discovered while sizing: the cluster-wide directory (registry.rs:52, cluster.proto GossipNode.cluster_addr) only carries each node's *cluster* gRPC address. KvService is currently registered on the client listener only (lib.rs:111, :142) — serve_cluster registers Raft/Admin/Gossip (lib.rs:180-187). So there is no existing path by which node A can issue a KV request to node B. Establishing one is the core of this task and the subject of Q1.

Also needs:
- Loop prevention — a forwarded request must never be forwarded again; a follower that receives a forwarded request and is not leader must fail, not bounce it onward.
- Leader identity, not just address: GgapError::NotLeader currently carries only Option<String>. Forwarding wants the leader's node_id so it can look the addr up in the registry rather than trusting the embedded one.
- Per-shard, not per-node: leadership is per shard (CLAUDE.md), so forwarding decisions are made per request against the routed shard.
- Connection reuse — do not dial a fresh channel per forwarded request; see GgapNetwork (network.rs:71) for the existing lazy-channel pattern.
- Observability: forwarded requests should be distinguishable in metrics/traces from locally-served ones.

Depends on tk-85c1, which makes NotLeader distinguishable from a generic consensus error on the linearizable-read path. (Done, merged as 933561a.)

## Scope widened 2026-07-25: AdminService too

Reported from the console: splitting a shard hits the same wall. Split is NOT the
tk-85c1 mapping bug — split.rs:149-157 already does the forward_to_leader() check
and admin_service.rs:203 deliberately surfaces NotLeader as a gRPC status rather
than burying it in the response body. Its mapping has always been correct. What it
shares with the KV browser is the second half: a correct leader hint the console
cannot act on.

The same applies to add_learner (admin_service.rs:143) and change_membership
(admin_service.rs:173) — pointed, since those are what you would use to join a
scaled-up node.

One asymmetry to carry into the spec: Q1's transport decision is moot for admin
ops. AdminService is already registered on the cluster listener (lib.rs:183) and
the console already reaches it over clusterTransport, so the node-to-node path
that Q1 exists to create for KV already exists for Admin. What the two surfaces
share is the mechanism, not the plumbing:

  resolve leader for shard -> dial peer from the gossip directory -> replay once
  -> never re-forward

Design it once as a shared component; both surfaces are applications of it. The
spec may propose shipping KV and Admin as separate PRs, and if it shows the whole
is too big for one task, convert to an epic then — with the design written once.

### Q1 [answered 2026-07-24T18:32:00+00:00] How does a node issue a KV request to the leader? The cluster-wide directory only knows cluster addrs, and KvService is only served on the client listener.
- a) Serve KvService on the cluster listener too — reuses the existing directory and the proto as-is; widens what the cluster port exposes, so the cluster port must stay non-public.
- b) Add an internal Forward RPC to cluster.proto — explicit forwarding envelope, easy to mark hop count and reject double-forwards; costs a new proto surface plus encode/decode of every KV request type.
- c) Gossip a client_addr alongside cluster_addr and dial the leader's client port — keeps the client API on one listener; adds a field to GossipNode and makes every node's client port reachable node-to-node.
> Serve KvService on the cluster listener too — register KvServiceServer in serve_cluster/serve_cluster_with_listener alongside Raft/Admin/Gossip. Reuses the existing gossip directory (cluster_addr) and the proto unchanged. Implication to honour: the cluster port now exposes the client API, so it must stay off the NodePort / off any public route.

### Q2 [answered 2026-07-24T18:32:00+00:00] What happens when the leader moves or is unknown while a request is being forwarded?
- a) Fail fast — return UNAVAILABLE with the leader hint and let the caller retry; simplest, and the console can retry cheaply.
- b) Bounded retry inside the server — re-resolve the leader and retry N times before failing; hides brief elections from the client, costs a retry budget and a deadline to respect.
> Fail fast — return UNAVAILABLE with the leader hint when the leader is unknown or moves mid-forward; the caller retries. No server-side retry loop, no hidden latency, no deadline budget to manage.

### Q3 [answered 2026-07-24T18:32:00+00:00] Does Watch forward too?
- a) Writes and linearizable reads only — Watch stays local and out of scope; smallest surface, streaming forwarding is its own problem.
- b) Watch forwards as well — consistent behaviour across the whole KV API, but proxying a long-lived server stream needs its own lifecycle and cancellation handling.
> Writes and linearizable reads only. Watch stays local and out of scope; proxying a long-lived server stream is a separate task if it turns out to be needed.
