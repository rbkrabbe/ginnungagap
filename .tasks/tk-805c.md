## Context

`--cluster-addr` and `--client-addr` are only ever inspected when their
`--*-listen-addr` counterpart is absent: `main.rs:171-189` resolves them through
`lookup_host` to derive a bind address. Supply both listen overrides and neither
advertised string is looked at before it goes into `NodeAddrs` and, from there,
into this node's own directory descriptor.

The k8s ConfigMap sets `--client-listen-addr`, so this is the deploy shape, not
a corner. A malformed advertised address survives startup and surfaces as a
dial failure from *other* nodes, at whatever later moment someone forwards a
request or Raft first contacts the peer — a long way from the node that has the
bad flag.

Where a bad address lands, after tk-ef8d: the node publishes it as its own
descriptor at this boot's incarnation, gossip carries it to every peer, each
peer persists it (tk-c593), and `GgapNetwork` resolves it on every RPC. So the
blast radius is wider than it was — the bad string reaches every node's
directory and survives their restarts — but it is no longer permanent. A typo
is now fixable by restarting the node with the corrected flag: the new boot
counter outranks every copy of the old descriptor. Before tk-ef8d the address
entered Raft membership and could not be changed at all, which is what made
this validation the only thing standing between a typo and unrecoverable
state. It is now a diagnosability fix, not a durability one — worth doing, but
sized accordingly.

This predates tk-d049 for `--cluster-addr`; that task extended the same shape to
`--client-addr` and is where it was noticed.

- `crates/ggap-node/src/main.rs` — validate both advertised addresses on the
  override path. The no-override path already fails loudly via `lookup_host`.
- Unit tests for the validator; no other crate is involved.

## Acceptance

- [ ] A malformed `--cluster-addr` or `--client-addr` fails startup with a
      message naming the flag, whether or not a listen override is set.
- [ ] A DNS name that is legitimately unresolvable at boot still starts (see Q1).
- [ ] Defaults, the README invocations and the k8s ConfigMap all still start.

### Q1 [answered 2026-08-21T19:49:38+00:00] How strictly should an advertised address be validated when a listen override means it is never resolved?
- a) Syntactic host:port only — catches typos and empty hosts, never fails on a peer DNS name that is not yet resolvable at boot; a well-formed but wrong name still gets through
- b) Full lookup_host resolution — catches wrong names too, but a node whose own DNS record lags its pod start now crash-loops where it used to come up
- c) Syntactic by default, resolution behind a flag — strictest available, but adds a flag to document and a second startup path to test
> a) Syntactic host:port only. Validate that each advertised address parses as host:port with a non-empty host and a valid port, on both the override and no-override paths; do not resolve on the override path. Rationale: the k8s deploy sets a listen override precisely because the advertised name is not locally resolvable at boot, so resolution there would crash-loop a pod whose own DNS record lags its start. A well-formed but wrong name still escapes to a later dial failure; that is accepted.
