## Context

tk-98e9 made a corrupt boot counter restart the count at 1, per its acceptance
criteria ("a warning, never a failure"). That is not only a lost guarantee. A
node publishing at 1 is superseded by any peer holding a higher incarnation for
its id, and `refresh_local` re-merges at 1 every tick, so it never wins its own
entry back: the node cannot correct its own address, and `exchange_with`
re-snapshots per peer, so it re-emits the stale address about itself. Permanent,
not transient.

A wiped data dir has the same shape and no remedy — the bytes are gone. A
corrupt counter does have one: the persisted directory lives in the same `node`
keyspace under a separate key, and its self-entry carries the incarnation this
node published on its last boot. Flooring the count at
`directory[self].incarnation + 1` repairs the rank whenever the two records do
not rot together, and degrades to today's behaviour when they do.

- Couples `BootCounter` to the persisted directory; consider whether the floor
  belongs in `BootCounter` or at the one call site in `main.rs`, which already
  loads both.
- Only a floor. A readable counter still wins, so the normal path is unchanged.
- Worth deciding whether the same floor should apply to an *absent* counter, or
  whether absent must keep meaning "first boot".
