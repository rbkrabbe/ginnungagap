## Context

The deletion this epic exists for. `GgapNode` (`config.rs:17`) loses its
`addrs` field and its `cluster_addr()` / `client_addr()` / `cluster_only()` /
`From<NodeAddrs>` surface. The type stays — openraft needs a `Node`, and it is
the home for a future consensus-only field.

Call sites: bootstrap `initialize()` in `main.rs`, `add_learner` (`node.rs:170`),
`not_leader()` (`node.rs:24`, which reads the address out of `ForwardToLeader`
and must resolve through the registry instead), the split's `initialize()`
(`split.rs:194`), and the four harnesses using `GgapNode::cluster_only`.

The `AddLearner` split — addresses to the directory at incarnation 0, ids to
membership — is inherited design; implement it here rather than restating why.

## What the change turned out to touch

Three things the context did not name, each forced rather than chosen:

- **`ClusterStatus` had to become id lists.** It exposed
  `Vec<(u64, NodeAddrs)>` straight out of membership, so it could not survive
  the deletion. `AdminService`'s hosted-shard path therefore resolves through
  the directory now, which is most of tk-00c0 — what is left there is the
  `last_observed_age_ms` semantics and confirming the two paths read as one.
- **The gossip task's membership-derived feed is gone.** It existed only to
  copy membership addresses into the directory at incarnation 0; with membership
  empty it had nothing to copy. Self-publication is now the only feed, which is
  what the epic wanted, but it means a node learns a peer's address *only* from
  that peer's own descriptor or from an `AddLearner` hint.
- **`SplitCoordinator` gained the registry.** `KvCommand::Split.source_members`
  still carries `NodeAddrs`, so they are resolved from the directory at split
  time; `ggap-node`'s `bootstrap_members` path merges them back in as hints on
  restart. tk-abf8 deletes both halves.

`GgapNode`'s `Display` impl went with the addresses — openraft's `Node` bound
never required it, and there was nothing left to print.

### Q1 [answered 2026-08-23T14:57:19+00:00] Membership no longer carries an address, so NotLeader's leader field must come from the directory or go away. Which address does the hint carry?
- a) client_addr — the hint's only consumer that cannot resolve ids itself is an external gRPC client reading ggap-leader-addr, and it dials the client port; in-cluster callers keep resolving leader_id themselves. Changes what ggap-leader-addr has always meant and flips assert_leader_hint_consistent to the client port.
- b) cluster_addr — status quo preserved bit-for-bit, no test or wire change, but ggap-leader-addr keeps naming a port no external client can use.
- c) Neither: drop leader, keep leader_id — no registry plumbing in OpenRaftNode/SplitCoordinator and no async not_leader; ggap-leader-addr stops being emitted and every consumer resolves through the directory. Narrowest code, widest wire change.
> client_addr

Accepted as-is, worth follow-ups rather than a block:
1. node.rs add_learner merges the hint into the directory before checking leadership, so an AddLearner sent to a follower still writes a permanent entry for a node that never joins (nothing removes directory entries — epic non-goal) and that entry then consumes a gossip fanout slot dialling a dead address every round. Bounded, self-correcting in the normal retry-at-leader flow, but a new side effect on a path that used to be a pure no-op.
2. split.rs:135-143 resolves source addresses with unwrap_or_default, so an unresolvable member lands in KvCommand::Split.source_members and bootstrap_members with empty addresses. Restart still works (membership takes the ids; merge_directory skips all-empty descriptors), but nothing logs the gap. tk-abf8 removes the field anyway.
3. benches/kv_write.rs seeds the directory with cluster_only descriptors, so not_leader now returns leader: None and the bench's ggap-leader-addr redirect branch is dead — it always falls through to scanning raft metrics. Seeding client addrs would keep that path exercised.
