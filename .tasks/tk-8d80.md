## Context

Today `AddLearner` takes a `NodeInfo` — node id plus both addresses — entirely
on the operator's word. Nothing verifies that the node at that address is the
node claimed, or that it is running at all. Two consequences:

- The id and the addresses can disagree. A node started as `--node-id 42` and
  added as `99` produces a directory entry and a membership id nothing can
  reconcile, undetectable from either side.
- The addresses are written into the leader's directory as an incarnation-0
  hint *before* the membership change, because the leader cannot dial the new
  node otherwise. On a follower the change fails and the hint stays (tk-346b).

The proposal inverts it: the leader dials the supplied address and asks the node
who it is. `GossipService.Exchange` already returns `sender_node_id` and the
responder's full view, and a fresh node self-publishes its own descriptor at
incarnation >= 1 whether or not it hosts a shard (tk-7664) — so one existing RPC
yields a verified id *and* the node's own descriptor, no hint required. The same
exchange seeds the new node with the cluster's directory, which is work the
leader's later Raft dial does today.

This supersedes tk-346b: with no hint written, there is nothing to write at the
wrong time. It also revises tk-ef8d's settled decision that "`AddLearner` writes
the new node's addresses into the leader's directory, at incarnation 0".

## Acceptance

- [ ] `AddLearner` establishes the learner's node id by asking the learner, not
      by trusting the request.
- [ ] An `AddLearner` naming an address that answers as a different node id is
      refused, with an error saying both ids.
- [ ] No incarnation-0 hint is written on the `AddLearner` path.
- [ ] The k8s bootstrap job still forms a cluster unmodified, or is updated in
      the same change.
- [ ] Full checklist green: fmt, clippy -D warnings, build, test.

### Q1 [open] Does AddLearnerRequest keep the node id?
- a) Drop it — the request carries addresses only and the id comes from the node. Cleanest end state, makes a mismatch unrepresentable, but breaks the console's add-node form, the k8s bootstrap job's grpcurl payload and the generated TS client.
- b) Keep it and validate — the leader compares the supplied id with what the node reports and refuses on mismatch. Backward compatible for every existing caller, fixes the same bug, but leaves a permanently redundant field and a rule about which source wins.
> unanswered

### Q2 [open] What happens when the learner does not answer the dial?
- a) Fail the AddLearner. Loud and correct — today an unreachable node is added and silently never joins — but the k8s bootstrap job adds nodes 2 and 3 and would now depend on them being up first.
- b) Fall back to the operator-supplied addresses and proceed as today. Keeps every existing deployment script working, but leaves the unverified path alive as the failure mode nobody tests.
> unanswered

### Q3 [open] The node answers but has not published its own descriptor yet — its first gossip tick has not run. Then what?
- a) Retry within a deadline. The descriptor is what makes the entry self-authored; waiting up to a second or two for it keeps sole authorship absolute.
- b) Accept sender_node_id alone and take the addresses from the request. The id is verified, which is the security-relevant half; the addresses are corrected by the node's own publication within a gossip round.
> unanswered

### Q4 [open] Does the incarnation-0 hint concept get deleted?
- a) Delete it. NodeDescriptor::hint and the incarnation-0 rank rule exist only for this path; removing them simplifies merge_directory's contract and the docs that explain it.
- b) Keep the mechanism, stop using it here. Costs nothing now and leaves a rank for a future caller that must write on another node's behalf — but keeps a rule in the code that nothing exercises.
> unanswered
