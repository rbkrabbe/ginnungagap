## Context

Today `AddLearner` takes a `NodeInfo` — node id plus both addresses — entirely
on the operator's word. Nothing verifies that the node at that address is the
node claimed, or that it is running at all. Two consequences:

- The id and the addresses can disagree. A node started as `--node-id 42` and
  added as `99` produces a directory entry and a membership id nothing can
  reconcile, undetectable from either side.
- The addresses are written into the leader's directory as an incarnation-0
  hint *before* the membership change, because the leader cannot dial the new
  node otherwise. On a follower the change fails and the hint stays (tk-346b).

The proposal inverts it: the leader dials the supplied address and asks the node
who it is. `GossipService.Exchange` already returns `sender_node_id` and the
responder's full view, and a fresh node self-publishes its own descriptor at
incarnation >= 1 whether or not it hosts a shard (tk-7664) — so one existing RPC
yields a verified id *and* the node's own descriptor, no hint required. The same
exchange seeds the new node with the cluster's directory, which is work the
leader's later Raft dial does today.

This supersedes tk-346b: with no hint written, there is nothing to write at the
wrong time. It also revises tk-ef8d's settled decision that "`AddLearner` writes
the new node's addresses into the leader's directory, at incarnation 0".

### Q1 [answered 2026-08-25T18:51:53+00:00] Does AddLearnerRequest keep the node id?
- a) Drop it — the request carries addresses only and the id comes from the node. Cleanest end state, makes a mismatch unrepresentable, but breaks the console's add-node form, the k8s bootstrap job's grpcurl payload and the generated TS client.
- b) Keep it and validate — the leader compares the supplied id with what the node reports and refuses on mismatch. Backward compatible for every existing caller, fixes the same bug, but leaves a permanently redundant field and a rule about which source wins.
> Drop it — addresses only. The id comes from the node, so 'id 99 at node 42's address' becomes unrepresentable rather than rejected. Console form, generated TS client and the bootstrap job change in the same PR.

### Q2 [answered 2026-08-25T18:51:53+00:00] What happens when the learner does not answer the dial?
- a) Fail the AddLearner. Loud and correct — today an unreachable node is added and silently never joins — but the k8s bootstrap job adds nodes 2 and 3 and would now depend on them being up first.
- b) Fall back to the operator-supplied addresses and proceed as today. Keeps every existing deployment script working, but leaves the unverified path alive as the failure mode nobody tests.
> Fail the RPC. An unreachable learner is refused rather than added-and-silently-absent, and the identity check can never be skipped. The k8s bootstrap job needs a per-target wait loop, since it currently waits only for the seed.

### Q3 [answered 2026-08-25T19:05:19+00:00] The node answers but has not published its own descriptor yet — its first gossip tick has not run. Then what?
- a) Retry within a deadline. The descriptor is what makes the entry self-authored; waiting up to a second or two for it keeps sole authorship absolute.
- b) Accept sender_node_id alone and take the addresses from the request. The id is verified, which is the security-relevant half; the addresses are corrected by the node's own publication within a gossip round.
> Accept sender_node_id alone; take the addresses from what was dialled. The id is the half with the safety consequence — both the reverse address check and the duplicate check key on it — and the node's own descriptor arrives within a gossip round regardless. No retry loop in an admin RPC.

### Q4 [answered 2026-08-25T19:05:19+00:00] Does the incarnation-0 hint concept get deleted?
- a) Delete it. NodeDescriptor::hint and the incarnation-0 rank rule exist only for this path; removing them simplifies merge_directory's contract and the docs that explain it.
- b) Keep the mechanism, stop using it here. Costs nothing now and leaves a rank for a future caller that must write on another node's behalf — but keeps a rule in the code that nothing exercises.
> Delete it. NodeDescriptor::hint and the incarnation-0 rank rule exist only for the AddLearner path, which no longer writes one. merge_directory's contract, registry.rs, ggap-types and the docs explaining it all simplify. A future caller needing to write on another node's behalf can reintroduce it deliberately.

### Q5 [answered 2026-08-25T18:59:18+00:00] What does the leader compare the returned node id against, to catch a node already in the group?
- a) Membership for the target shard — authoritative and never stale; a node that legitimately moved is re-added without trouble.
- b) Membership plus the directory's address for that id — also catches a node answering somewhere unexpected, but false-positives on a node that moved and has not republished yet.
- c) Membership across every shard this node hosts — stricter, but a node hosting several shards legitimately appears in each, so it would refuse valid adds.
> Reverse lookup: reject when the directory already maps a different id to the address just dialled. Catches a node that restarted under a new id at the same address — the case membership alone misses, because the returned id is genuinely absent from membership while the process is already serving the old id there. The forward lookup (id -> address) is the one that false-positives on a node that moved, so it is not used.

### Q6 [answered 2026-08-25T18:59:23+00:00] A stale directory entry now blocks reusing its address, and nothing retracts one. How is that handled?
- a) tk-c47e first — directory-entry removal becomes a prerequisite, so refusing is safe because there is a supported way to clear a decommissioned node.
- b) Refuse with the conflicting id in the error, no removal mechanism yet.
- c) Refuse, with an explicit force flag to overwrite the entry.
> tk-c47e becomes a prerequisite. Directory-entry removal lands first, so refusing a reused address is safe: there is a supported way to clear a decommissioned node rather than a permanent block or a force flag that ends up in every runbook.

### Q7 [answered 2026-08-25T18:59:23+00:00] Does the reverse address check also run outside the join path, to detect a duplicate that already exists?
- a) Join path only — keeps this task bounded to the join protocol; an already-corrupted directory stays undetected until someone re-adds that address.
- b) Also at gossip merge — catches the state however it arose, but widens this task or wants its own.
> Join path only. Keeps this task bounded to the join protocol; a directory already holding two ids for one address stays undetected until someone re-adds that address.
