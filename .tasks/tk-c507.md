## Problem

The gossip directory maps `node_id -> cluster_addr` only (registry.rs:55). Per
tk-3846 Q7 forwarded client traffic goes to the leader's *client* port, so a
forwarder has no address to dial. Nothing in the cluster knows any node's client
address today — `--client-addr` is a bind address (`0.0.0.0:17000`,
deploy/k8s/ggap/configmap.yaml:23), never advertised anywhere.

This carries the second address through proto, registry and gossip task. It
changes no request path; tk-2cb2 consumes it.

## Approach

The directory value becomes a two-field `NodeAddrs { cluster_addr, client_addr }`
and merges **field-wise**: an empty field is ignored, never written over a known
one. That rule is load-bearing, not tidiness — `refresh_local` feeds the
directory from Raft membership (gossip.rs:131-139), which carries `cluster_addr`
only, so a whole-value merge would erase every client_addr once per second.

Each node derives its own advertised client_addr as host-of-`--cluster-addr` +
port-of-`--client-addr`, and seeds it into the directory alongside cluster_addr
(gossip.rs:120-122); gossip spreads it from there. Rejected: a new
`--advertise-client-addr` flag (Q1) — derivation is correct for every current
deployment and costs no manifest change. A deploy that ever splits the two ports
across hostnames adds the flag then.

## Risks

- The once-per-second `refresh_local` membership merge is the exact path that
  field-wise merging exists to protect. A test that only exercises
  `merge_directory` directly will pass while the real task erases the field —
  the three-node assertion above must run *after* several gossip rounds, not
  after one seed.
- Mixed-version cluster: an old peer echoes back a directory with empty
  client_addrs. Field-wise merge makes that a no-op rather than a regression.
- `snapshot_for_gossip`'s return type changes; `gossip_service.rs` and the
  registry tests are the callers.

## Outcome

Spec approved mid-implementation after the scope hook resized this `m -> l`;
finished in the same session.

The convergence test was mutation-checked, since the spec called out that a
weak version of it would pass against a broken merge: replacing the field-wise
body of `merge_directory` with `dir.insert(node_id, addrs)` makes
`gossip_converges_on_every_node_client_addr` fail at the convergence loop
("gossip never converged on all client addresses"), and reverting it passes.
The failure is not subtle, and the reason is worth recording: `refresh_local`
seeds self *before* merging membership, and self appears in its own shard's
membership, so a whole-value merge blanks a node's own client address in the
same tick it sets it. The empty value then propagates to every peer. So the
field-wise rule is not protecting against a rare interleaving — without it the
feature never works at all.

The observer node in `start_observer` turned out to be a free test of the
"advertises no client address" path: it hosts no shards and serves no client
API, so it gossips an empty `client_addr` forever while still learning
everyone else's.

Two judgement calls made while implementing:

- A wildcard `--cluster-addr` (`0.0.0.0:17001`) derives a wildcard client host
  rather than `None`. Nothing in the node knows a better hostname, and Raft could
  not dial such a node either, so this is not a new failure mode. Pinned by
  `wildcard_cluster_addr_derives_a_wildcard_host`.
- Derivation failure warns and gossips an empty address (merged away as
  "unknown") instead of failing startup. Refusing to boot would turn a forwarding
  limitation into an outage.

`docs/ggap-consensus.md:72-74` was updated too (not in the Changes list above):
it described `ShardRegistry` + `GossipTask` as a view of "which node hosts which
shard", which stopped being the whole truth once the directory carries an address
the forwarder depends on. The new text records *why* the two addresses merge
differently, since that is the part a future reader would otherwise undo.

Discovered, filed, not fixed here:

- **tk-7664** — `refresh_local` early-returns when a node hosts no shards,
  skipping both the self-seed and the membership merge. Harmless today, and it is
  why `ShardRegistry::new` keeps seeding both addresses rather than leaving it to
  the gossip task.
- **tk-1bf0** (from adversarial review) — directory entries carry no version, so
  a *changed* address has no monotonicity rule and stale copies can overwrite
  fresh ones. Pre-existing, but it bites harder now: `cluster_addr` is masked by
  the per-tick membership re-derivation, `client_addr` has no such repair. Worth
  closing before tk-2cb2 caches a channel per node id.

Review verdict `pass`. The reviewer independently mutated `node_to_proto` to emit
an empty `client_addr` and confirmed both integration tests fail, which
establishes that they ride the real gRPC gossip path rather than an in-process
struct copy — a stronger check than the one recorded above.

Left deliberately: `node_from_proto` is `pub` with no cross-crate caller. Its
sibling `entry_from_proto` is too; the `*_to_proto` / `*_from_proto` pairs in
this file are uniformly `pub`, so narrowing one half of one pair would cost more
in consistency than it gains.
