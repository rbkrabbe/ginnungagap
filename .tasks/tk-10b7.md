## Context

The split path has its own copy of the address problem, and it is the one place
where losing an address is not merely inconvenient: a shard created by a split
bootstraps its Raft group from these records, so whatever they omit, the new
shard never had.

`KvCommand::Split.source_members` is `BTreeMap<u64, String>`
(ggap-types/src/lib.rs:106). It travels in the Raft log *and* is persisted as the
`bootstrap_members` meta key (fjall.rs:504), then read back at startup to
initialize a split-created shard (main.rs:256-268, split.rs:193).

- `ggap-types/src/lib.rs:106` — `BTreeMap<u64, NodeAddrs>`.
- `split.rs:120,144` — build it from `GgapNode` membership rather than `.addr`.
- `fjall.rs:430-504` — encode/decode the wider type.
- `main.rs:256-268` — decode and construct `GgapNode` with both addresses.

Format break on both the log and the meta keyspace; wipe, per the epic's Q2.

Runs in parallel with tk-fd58 — both depend on the flip, neither on the other.

## Outcome

`KvCommand::Split.source_members` is `BTreeMap<u64, NodeAddrs>`. The split
coordinator hands the whole membership entry over — `NodeAddrs::from(GgapNode)`,
the reverse conversion tk-441f left for its first caller — instead of projecting
it down to `cluster_addr`. `main.rs` decodes the wider type and rebuilds
`GgapNode` from it, so the two paths a split-created shard is initialised
through, the live one and the restart one, now carry the same value.

Format break on both the Raft log and the `bootstrap_members` meta key, per the
epic's Q2: a stale data dir fails as a bincode decode error.

**Nothing populated `client_addr` in the split tests before this.**
`split_single_node.rs` initialised its single node with `GgapNode::default()`,
so a coordinator that kept dropping the client address would have passed every
assertion in it. Setup now uses both addresses and
`split_carries_both_addresses_to_new_shard` checks the new shard's live
membership and its persisted `bootstrap_members`; the `split_crash_bugs.rs`
fixtures carry both addresses for the same reason.

**Three comments naming tk-10b7 as owed work are gone, not renamed.**
`config.rs`, `node.rs:ClusterStatus` and `gossip.rs` each recorded that a
split-created shard was the one place `client_addr` stayed empty. That is no
longer a condition of the code. The field-wise merge in `merge_directory` still
has a reason to exist — an uninitialised shard has empty membership — so the
gossip comment was rewritten to say that, pointing at tk-11b6.

**Reviewed locally.** The `adversarial-reviewer` subagent this task's size
requires was not configured in the cloud environment the work was done in, and
`tk` was not on its PATH there, so the review was run in a local session
instead; see the Review section below.

**`sim_cluster.rs` has no split coverage** despite the acceptance line naming
it; the split path is exercised by `split_single_node.rs` and
`split_crash_bugs.rs`. Nothing in `sim_cluster.rs` needed changing and its seven
tests pass.

**Only the persisted assertion is load-bearing.** The review mutated
`split.rs:145` back to `cluster_only` and found the live-membership assertion at
`split_single_node.rs:225` still passed — the coordinator initialises the new
shard from the `GgapNode` map directly, not from the command, so only the
`bootstrap_members` assertion at `:245` catches a regression here. Accepted, but
worth knowing before either assertion is touched.

**The `touched` array here was restored by hand.** Every `tk` write reads it
back as the string `"["` and persists that, dropping all ten paths; `tk review`,
`tk claim` and `tk done` each did it. Noted because the field is load-bearing for
the commit-scope hook, so anyone re-running `tk` against this file should check
it afterwards.
