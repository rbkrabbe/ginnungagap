## Context

`OpenRaftNode::add_learner` (`ggap-consensus/src/node.rs`) merges the joining
node's addresses into the directory *before* calling `raft.add_learner`, so the
leader can resolve the learner by the time replication to it starts. The
ordering is deliberate and correct on the leader.

On a follower it is not. The RPC fails with `NotLeader` and no membership change
happens, but the hint is already written, and nothing removes a directory entry
(tk-c47e). Gossip then spreads an entry for a node that never joined. The
addresses are the caller's to supply, so this is a way for any client that can
reach a follower to plant an arbitrary node id in every node's directory.

Checking leadership first is racy — leadership can move between the check and
the write — so the fix is more likely to be writing the hint only on success,
which needs the learner to be resolvable *during* `add_learner` and therefore a
look at whether openraft begins replicating before the call returns with
`blocking = false`.

## Acceptance

- [ ] An `AddLearner` that returns `NotLeader` leaves the directory unchanged.
- [ ] A learner added on the leader is still dialable, asserted as it is today.
